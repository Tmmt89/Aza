## Правила (не нарушать)

1. Официальный ДУМ или мечеть — первичный источник.
2. Sajda и 1Muslim — только контроль качества, в продукт не попадают.
   Условия 1Muslim прямо запрещают переиспользование контента.
3. Расчёт — явно обозначенный резерв, а не молчаливая подмена.
4. Источники не смешиваются молча: смена источника меняет подпись.
5. Ни одно расписание не попадает в публичный релиз без письменного
   разрешения правообладателя.

## Как это работает в приложении

Города каталога добавляются в список выбора автоматически (сопоставление
по нормализованному названию: идентификаторы каталога кириллические, наши
латинские). У таких городов нет координат — и это сознательно: выдумывать
координаты посёлка ради «красивого» резервного расчёта значит показывать
выдуманное время намаза. Пока таблица покрывает день — работает она;
когда покрытие кончается, город без координат честно остаётся без времён.

Проверено вживую: Казань и Москва берут таблицу (ДУМ РТ, ЦДУМ),
Челябинск — таблицу внутри своего диапазона, Грозный — расчёт с явной
подписью, Агрыз (город только из каталога, без координат) — таблицу
ДУМ РТ. Тест `testDayOutsideTableCoverageFallsBackAndRelabels`
закрепляет правило смены подписи при выходе за покрытие.

Что закрывает правила в коде:

- подпись берётся у ИСТОЧНИКА ГОРОДА, а не у общего ярлыка файла —
  сводный каталог не может подписать времена одного муфтията именем
  другого (`testCitySourceWinsOverCatalogWideLabel`);
- источники, разрешённые владельцем только для сверки (Sajda, 1Muslim),
  отклоняются при загрузке целым файлом (`testQAOnlySourcesAreNotUsableInProduct`);
- одноимённые города без возможности различить — отказ вместо догадки;
- несколько годовых файлов сливаются, а нужный снимок выбирается по
  покрытию дня; день берётся из выбранного снимка, а не по идентификатору
  (`testCollidingIdentifiersDoNotLeakDaysAcrossSnapshots`);
- в интерфейсе подпись сегодняшней сетки и подпись ближайшего намаза
  разделены: после иши ближайший намаз уже завтрашний и может прийти из
  другого источника.

## Открытый вопрос: данные в истории git

В `Design/Aza-current-states.svg` макет показывал НАСТОЯЩЕЕ расписание
ДУМ РТ (Казань, 23.08.2026) — шесть значений. В рабочем дереве они
заменены на синтетические, но остаются в первом коммите `b1c9211`,
который уже опубликован в публичном репозитории на GitHub.

Решение за владельцем: оставить как есть (шесть значений за один день —
вероятно, ниже порога охраноспособности) или переписать историю с
force-push. Второе затрагивает опубликованную ветку, поэтому без явного
распоряжения не делается.

Отдельно: локальные служебные ссылки `refs/codex/turn-diffs/*` (снимки
рабочего дерева, которые делает инструментарий Codex) содержат прежние
значения. Они не отправляются на сервер — `git push` по умолчанию
отправляет только `refs/heads`, а собственный push-refspec у remote не
задан. Удалять их сейчас нельзя: Codex использует эти контрольные точки в
текущей сессии. Почистить можно потом: `git for-each-ref
--format='%(refname)' refs/codex | xargs -n1 git update-ref -d`.

Проверка на будущее автоматизирована: `Tools/check-schedule-leak.sh`
сравнивает трекаемые файлы со всеми установленными каталогами (той же
папкой, откуда читает приложение, регистр расширения не важен). Четыре и
более подряд идущих значения из одного дня — отказ, код 1. Три подряд —
предупреждение: времена намаза структурно похожи, и расчётный вывод
случайно совпадает с фрагментами настоящих таблиц (проверено: вывод adhan
для Грозного совпал по трём значениям с городами Татарстана на другую
дату, ничего не копируя). Без установленных каталогов — код 2, чтобы
зелёный CI не выдавали за пройденную проверку.

**Границы метода** (не выдавать его зелёный за доказательство):

- одиночное значение не детектируется в принципе — в каталоге
  встречается 1401 из 1440 возможных значений `ЧЧ:ММ`. Настоящий аср,
  вставленный в макет, скрипт не поймал: его нашёл Codex целевым поиском;
- скопированный день, у которого подправили значение **в середине**, тоже
  проходит: непрерывных четвёрок после этого не остаётся. Подмена
  первого или последнего значения ловится.

За тем и другим нужен ревьюер, а не только скрипт.

   машиночитаемых наборов нет. До их получения города считаются расчётом.
6. **Подпись каталога.** Сейчас происхождение самодекларируемое: файл сам
   заявляет имя источника, ссылку и SHA-256, и никто это не сверяет с
   первоисточником. Предложение Codex, с которым я согласен: отделённая
   подпись Ed25519 на манифест (SHA-256 + URL + издатель), доверие ключу
   по принципу TOFU при первом импорте — без списка «правильных»
   организаций. До подтверждения ключа каталог помечается как
   «происхождение не подтверждено» и НЕ получает `isVerifiedTable`.

## Ограничения данных

- Каталог на 2026 год. В 2027 покрытие закончится: города с координатами
  перейдут на расчёт, города без координат останутся без времён, пока не
  появится новый каталог.
- У ДУМ РТ Фаджр берётся из официальной колонки «Завершение сухура» —
  это отражено в исходных данных и объясняет заметное расхождение с
  астрономическим расчётом (около часа). Конкретные значения здесь не
  приводятся: файл репозитория не место для данных, на которые нет
  разрешения.
- У календарей ЦДУМ по изображениям (Уфа) импорт не выполнялся.
